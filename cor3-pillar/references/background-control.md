# 后台控制与界面卡顿

连上浏览器只是前提，动手前还得确认两点：操作时窗口会不会弹到前台，后台里的游戏画面有没有还在绘制。优先用这个号已经测通的工具；这份说明对适配器型号不作强制要求。

## 接入前先核实

- 从本地会话记录拿到本号明确的账号、profile 和标签页，只连自己那一套配置，别混用别的号的默认值、旧 PID 或调试端口。多号各自保留自己的连接和进度。
- 先拿只读动作测一下：会不会把窗口弹到前台，原有标签页是不是还留着。浏览器大版本升级或换了控制方式，重新测一次。
- 用后台适配器时，先实测确认它做得到这几件事：不激活窗口就能恢复绘制、复用本号的空白页或游戏页、只读可见界面并点击、用完断开、关掉或清掉游戏页并核实没留标签。缺哪一步如实写出来，单靠 UIA 或 `background:true` 还不足以证明真后台。
- 用户正在用目标窗口时让出控制权，收尾也留着用户正在看的页面。碰到登录掉线、验证码、权限限制或工具安全策略拒绝，按工具规则停下汇报，禁止换接口硬绕。

## 实测范围：Windows / BitFox 128

2026-11-09 在一个 Windows / BitFox 128 环境里测到：浏览器最小化后游戏加载停在 IWT 0%，信号解码控件直接隐藏；在不激活窗口的前提下恢复后台绘制后画面恢复，并顺利领到日常奖励。同一环境下 `Target.createTarget` 就算传了 `background:true` 照样抢前台，改成复用已有空白页才稳定在后台跑。换了 BitFox 版本或遇到别的卡顿，仍要按实测确认。

用已验证的后台适配器时按这个顺序走（具体命令、路径和依赖看本地接入记录，实际路径由本地配置提供）：

1. 核对账号归属、确认用户没在操作目标窗口，恢复不激活窗口的后台绘制。
2. 复用该号的游戏页或空白页，连上后等页面真正就绪再读可见状态。
3. 点一下等状态变了再动下一步，必要时重新拉快照定位可见控件。
4. 收尾断开连接，关掉本次游戏页或导回空白页，确认没遗留游戏页；浏览器、登录状态和其他标签留着。用户要求最小化就最小化回去；如果发现用户已经接管窗口，保持原状。

## 卡顿时按顺序排

先分清是新手引导没点完、页面还在异步加载、碰到了隐藏重复按钮、漏了二次确认弹窗、软件格式或 Power 不够、服务器维护，还是后台渲染停了。读清卡片上下文、可见尺寸和启用状态再点控件；只操作可见且可用的界面元素，禁止强行把隐藏节点改成可见，也禁止直接调隐藏游戏逻辑跳过正常交互。

允许短等几秒，但成不成一律以消息出来、任务栏更新、余额变化或列表刷新为准。交易没看清成没成先对账；确认没有小游戏、付款确认框或倒计时在跑再刷新。就算刷新后恢复了，也只记下“本次刷新后恢复”的事实，没查出根因就写未确定。
