# 后台控制与界面卡顿

“能连接浏览器”不等于“不抢用户窗口”，也不等于游戏仍正常绘制。执行前核对当前控制方式的真实行为，优先沿用该账号已经验证的工具；本文件不要求安装特定适配器。

## 接入要求

- 从本地会话映射取得明确的账号/profile/标签，不硬编码其他账号的默认值、旧 PID 或调试端口。多个账号分别持有连接和进度。
- 先用不改变游戏进度的操作验证前台窗口是否保持不变、原标签是否保留。新浏览器版本或控制方式变更后重新验证。
- 已有后台适配器时，期望提供：不激活窗口的绘制恢复、复用本账号游戏页/空白页、可见界面读取与操作、断开连接、卸载本账号游戏页及标签核验。缺少能力时如实说明，不能把 UIA 或 `background:true` 当作证明。
- 用户正在使用目标窗口时不接管，也不在收尾关闭用户正在操作的页面。登录失效、验证码、权限或安全检查拒绝按当前工具规则处理，不换接口规避。

## 实测范围：Windows / BitFox 128

2026-11-09 的一个环境中，最小化后游戏启动停在 IWT 0%，信号解码控件隐藏；允许窗口在后方绘制且不激活后恢复，并完成日常奖励。该环境的 `Target.createTarget` 即便设置 `background:true` 仍抢前台，复用已有空白页才符合用户后台要求。没有证明所有 BitFox 版本、所有加载停滞都如此。

已验证的适配器可采用以下顺序；具体命令、路径和依赖来自本地接入记录，不在公共 skill 中猜测：

1. 核对账号归属、用户未使用目标窗口，恢复不激活的后台绘制。
2. 复用对应游戏页或空白页，连接后等页面实际就绪，再读可见账号状态。
3. 单次操作后等待状态变化；必要时重新取得快照和可见控件。
4. 收尾断开连接，关闭或导航为空白的本次游戏页，验证没有遗留游戏页；保留浏览器、登录和其他标签。再按用户要求最小化，若用户已经接管则保持原状。

## 排查顺序

先区分未完成引导、异步加载、隐藏重复控件、缺确认弹窗、软件/权限不足、维护和渲染停滞。读取上下文、可见尺寸和启用状态后再选控件；不能把隐藏节点改成可见或直接调用隐藏游戏逻辑来跳过正常交互。

允许短暂等待，但应以实际消息、任务状态、余额或列表变化判断完成。交易结果不明先核账；未完成小游戏、支付确认或其他计时操作时不盲目刷新。刷新有效也只记录该次恢复，不伪造根因。
